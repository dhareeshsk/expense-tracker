## 6. §17 Push Notifications

Status: ✅ Done — re-verified in code and live-tested (2026-09-13). Built in one full pass per your decisions: self-managed Web Push (not a managed provider), all three triggers (household activity, budget thresholds, reminder due/overdue), bell + real push together.

- [x] `PushSubscription` and `Notification` models added to `prisma/schema.prisma`, migrated cleanly. **One deliberate deviation from the spec's minimal `Notification` shape**: added a nullable `relatedId String?` field, needed for two things the spec's model as literally written couldn't do — deep-linking a notification to its actual source (a household, a reminder, a budget's category) and de-duplicating repeated alerts (see below). Indexed `(userId, isRead)`, `(userId, createdAt)`, and `(type, relatedId, createdAt)`.
- [x] `web-push` installed, a real VAPID key pair generated and stored in `.env` (`NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`) — **you'll need to set the same three in Vercel's production env vars**, same as the other secrets I've flagged throughout this project.
- [x] `src/lib/push.ts` (`sendPushToUser`) and `src/lib/notifications.ts` (`createNotification`, `hasRecentNotification`) — shared helpers used by every trigger. Push delivery is deliberately best-effort: a failed send (expired subscription, no subscription, VAPID unconfigured) never blocks the caller, and a 404/410 response from the push service auto-deletes the stale subscription.
- [x] `/api/push/subscribe` and `/api/push/unsubscribe`, plus `src/lib/push-client.ts` (browser-side: requests Notification permission, subscribes via the service worker's `PushManager`, POSTs the subscription).
- [x] `public/sw.js` — added real `push` (shows the OS notification) and `notificationclick` (focuses an existing tab or opens one, navigating to the notification's target URL) listeners, on top of the existing PWA shell-caching logic.
- [x] **In-app notification bell** (`src/components/notification-bell.tsx`), wired into `site-header.tsx` for logged-in users — unread-count badge, dropdown list (polls every 60s), "Mark all read", click-to-navigate (reminder → `/reminders`, budget_alert → `/budgets`, household → `/households/[id]`), and an inline "Enable push notifications" prompt when push isn't yet subscribed in that browser. Works independently of push permission, per the spec's explicit requirement that users who decline push still see alerts in-app.
- [x] **All three triggers wired in**:
  - *Household activity* — `POST /api/transactions` now notifies every other household member when a shared transaction is added; `POST /api/households/[id]/invite` notifies an invited *existing* user (can't notify someone with no account yet — out of scope, same as before).
  - *Budget threshold* — added to the cron sweep: checks every budget's current-month spend against its `alertThreshold`, de-duplicated via `relatedId` + `hasRecentNotification` so it fires once per budget per month while still over, not once per day.
  - *Reminder due/overdue* — extends the §14 cron sweep: a reminder due **today** (not yet overdue) now also gets a one-time-per-day notification, alongside the existing overdue→MISSED flip.

**A real bug found and fixed during verification, not just claimed:** the overdue-reminder sweep originally compared `dueDate < now` (the exact current instant). Since due dates are stored as midnight, this meant *any* reminder due "today" would already read as overdue the moment any time had passed since midnight — so it would get swept straight to MISSED before the new "due today" notification branch ever had a chance to fire, silently defeating that whole feature. Caught this by actually running the cron sweep against a reminder due at the current moment and finding `reminderDueTodayNotifications: 0` when it should have been 1. Fixed by comparing against the start of the current calendar day instead, so a same-day reminder now correctly stays PENDING (with a due-today alert) until the day is actually over.
